6.1
Pillar 1 · Tiered access & policy

Who can reach what

A two-axis policy: role × data classification — wired into Copilot's policy system.

Engage

A junior, via an agent, just read a restricted dataset.

The agent inherits — and amplifies — access
Without a tiered policy, the agent's reach is the union of everything its user, its MCP servers, and its cloud environment can touch. That's a finding waiting to happen.
Theory

Two axes, four data tiers

Data tiers
Public · Internal · Confidential · Restricted (safety-critical calibration, customer IP, credentials).
Role tiers
Junior + agent · Senior · SRE/DevOps · Principal/architect — each row gets allow / gate / deny per data tier.
Enforcement, not documentation
GitHub roles + repo permissions · Copilot policies · MCP allowlists · content exclusion. The matrix is only real where a control enforces each cell.
Theory

Copilot's policy system — the actual knobs

  • Three policy types: Feature · Privacy · Models.
  • ~17+ enumerated policies — cloud agent, code review, MCP servers, web search, content exclusion, custom models…
  • Set at enterprise (locks orgs) or org level.
Conflict resolution is per-policy
Not a flat "most restrictive wins" rule — each policy resolves enterprise/org conflicts its own way. Verify the policy you care about; don't assume.
Model restrictions
Admins can restrict the model picker by policy — e.g. only Anthropic GA models (zero-data-retention: the vendor stores no prompts or outputs) for regulated repos.
Theory

Content exclusion — and its real limitations

What it does
Business/Enterprise: YAML path rules (fnmatch) suppress Copilot suggestions in matched files — calibration data, key material, restricted IP.
What it does NOT do
Not honored in Copilot CLI, the cloud coding agent, or Agent/Edit modes of Chat · up to 30-min propagation · Copilot "may use semantic information from an excluded file if the information is provided by the IDE indirectly." Best-effort — not a guarantee.

6.2
Pillar 2 · Mandatory human gates

What an agent may never do alone

Some actions require a human to say yes — every time.

Engage

Samsung, 2023: engineers pasted source into a chatbot. Three leaks in twenty days.1

The lesson
Good intent isn't a control. Certain actions must hit a hard gate: destructive ops · credential creation/rotation · force-push to protected branches · threshold changes in safety-critical code · hardware bench access.
Theory

Three enforcement layers in the Copilot stack

1 · PreToolUse hooks
.github/hooks/*.json — a gate script on preToolUse exits non-zero to block. CLI: GA · VS Code: Preview. Commit to the default branch for cloud-agent runs to pick it up.
2 · Permission levels
Default Approvals · Bypass Approvals · Autopilot (Preview). Never Autopilot in regulated repos.
3 · Platform guards
Protected branches + required reviews + protected environments bound the cloud agent — its draft PR cannot merge itself.

6.3
Pillar 3 · Isolation patterns

Contain the blast radius

Match the isolation level to the risk class.

Theory

The sandboxing spectrum

  • Shared-kernel container — fastest (~500 ms class), weakest boundary.
  • gVisor — user-space kernel (~100 ms class), stronger.
  • Firecracker / Kata microVM — hardware isolation; the high-risk default.
2026 consensus
Never run untrusted AI-generated code in shared-kernel containers.
Copilot's built-in boundary
The cloud agent runs in an ephemeral GitHub Actions sandbox — isolated per task, destroyed after. Complement it with read-only containers, a private VPC + egress proxy for self-hosted runners, and a worktree per agent (a separate git working copy per agent) for parallel local work.

Theory

2026 reality: agent sprawl & agent identity11 Facts as of Jul 2026

Sprawl
Gartner: the average Global 500 firm will run >150,000 agents by 20286 (directional forecast — treat as a trend signal); >40% of agentic projects canceled by end-20277; only ~13% of orgs believe their agent governance is right.
Identity
Agents need first-class identities — Microsoft Entra Agent ID (GA ~Apr 2026): agent identity blueprints, OAuth flows, Conditional Access. Every custom agent you shipped this course should be inventoried, owned, and revocable.
6.6
Pillar 6 · Audit, metrics & cost

Prove it — and keep the bill honest

GitHub's audit trail, its gap, the metrics API, and hard budgets.

Engage

The quarter's AI-credit bill arrived. Nobody saw it coming.

No metrics, no mandate
Without spend attribution, override rates and agent-vs-human traceability, you can't defend the program — or renew its budget.
Theory

The audit trail — and the gap you must close

What GitHub logs
Audit log (action:copilot): plan, policy and seat changes, plus website agent activity. ~180-day retention.
What it does NOT log
Client-side prompts — what your engineers send from the IDE and CLI never reaches the audit log. Close the gap yourself: hooks → JSONL → SIEM (your security-event store). Your 6.2 gate set already emits the events.
Theory

What to measure Facts as of Jul 2026

Sources
Copilot usage metrics API — GA; NDJSON (newline-delimited JSON) reports, 1-day + 28-day, ~1-year retention (legacy Metrics API closed Apr 2026). Plus your hook traces.
DORA + SPACE
The two standard delivery-metrics frameworks (DORA: DevOps Research & Assessment8; SPACE: developer-productivity dimensions9). Deploy frequency, lead time, change-fail rate, MTTR — plus the human dimensions a single metric misses.
Team-level agent signals
Credit spend per developer · % PRs with AI review · bugs caught pre-merge · override rate · agent-vs-human traceability (ISO 26262 evidence12).
